# ランドスケープ更新手順

このファイルは、`docs/` のツール・ランドスケープを定期的に更新するための手順書。
人が読んでもエージェントが読んでも同じ動作になるように書いてある。
`/update-landscape` から呼ばれるほか、定期実行のプロンプトとしてもこれを使う。

作業ディレクトリはリポジトリのルート（`README.md` がある階層）。

---

## 目的

このランドスケープは放っておくと必ず腐る。ツールは改名し、組織を移り、アーカイブされ、
新しいものが出てくる。**その変化を、推測ではなく実測と公式情報で追随させる**のがこの手順の目的。

## 成功条件

以下がすべて満たせたら完了。

1. `docs/data/metrics.json` が最新の実測値になっている（または実質的な変更が無いと確認できた）
2. 改名・移転・アーカイブ・終了が検出され、`docs/registry.yaml` に反映されている
3. 新しく登場したツールが検討され、追加したものには出典と確認日が入っている
4. `uv run docs/build.py` が警告ゼロで完走する
5. 変更点の要約が出力されている

---

## やること

### 1. 実測値を更新する

```bash
uv run docs/fetch_metrics.py
```

出力の末尾に注目する。

- **「改名 / 移転を検出」** が出たら、`docs/registry.yaml` の当該項目の `repo` を新しい値に直す。
  そのうえで **なぜ移ったのかを調べる**。組織移管や買収は、それ自体がランドスケープの重要な情報なので、
  `summary` と `sources` に反映する。直したら `fetch_metrics.py` を再実行する。
- **「取得失敗」** が出たら、リポジトリが消えたか非公開になった可能性がある。
  調べて、消えていたら `repo: null` にし、`ended` と `succeeded_by` を埋める。
  **失敗した項目の前回値はスクリプトが温存する。null で上書きされることはない。**

### 2. 状態が変わった項目を洗い出す

```bash
uv run docs/build.py
```

前回の `index.html` との差分を見て、状態（勢いあり / 現役 / 停滞 / 終了）が変わった項目を特定する。
特に **`stale` に落ちた項目と `archived` になった項目**は、公式に何かあった可能性が高いので個別に調べる。

### 3. 終了・改名・統合を反映する

終了が確認できたら、その項目に以下を埋める。

- `ended` — 終了年月（`YYYY-MM`）
- `succeeded_by` — 後継がある場合、その slug。無ければ `null`
- `tier: history` — 終了したものは詳細ティアから降ろす
- `summary` — 「いつ、なぜ終わり、どこへ行ったか」を一文で
- `sources` と `verified` — 公式アナウンスの URL と確認日

**終了した項目を削除してはいけない。** 墓場が残っていないとタイムラインが意味を失う。

### 4. 新しいツールを探す

新規追加は、印象ではなく外部の判断を根拠にする。次のいずれかに該当するものを候補にする。

- 既存 L2 ツール（Headroom など）が新たに統合対象に加えたエージェント
- 既存項目の後継・フォークとして公式に案内されたもの
- 既存項目と同じ層で、GitHub の star がこのリポジトリの自動昇格ライン（25,000）を超えているもの

追加するときは `docs/registry.yaml` の末尾に、既存項目と同じフィールド構成で書く。
値が分からないフィールドは `null` のままにする。

### 5. ティアの線引きを見直す

`build.py` が自動で判定するので、通常は何もしなくてよい。
手動昇格（`tier: detail` + `tier_reason`）を足す場合は、**理由を必ず書く**。画面に表示される。

自動で詳細ティアに上がった項目には、`docs/tools/<slug>.md` の本文が要る。
無いと `build.py` が警告を出すので、書くか、`tier: history` を明示して降ろす。

### 6. 再ビルドして確認する

```bash
uv run docs/build.py
```

**警告が残っている状態で終わらせない。** 警告は「確認日が無い」「出典が無い」「本文が無い」のいずれか。

### 7. 変更点をまとめる

最後に、この回で何が変わったかを報告する。形式は「やらないこと」の下に示す。

---

## やらないこと

ここが一番大事。以下は明示的に禁止する。

- **裏が取れない値を埋めない。** 公式ドキュメント・公式アナウンス・GitHub API のいずれかで
  確認できないものは `null` のままにする。それらしい値を書くくらいなら空欄のほうがよい。
- **実際に確認していない項目の `verified` を進めない。** 一括で日付を書き換えるのは禁止。
  その項目の出典を実際に見たときだけ更新する。
- **判断基準を勝手に変えない。** 状態の判定ルール（90 日 / 180 日 / リリース 10 件）と
  詳細ティアの自動昇格ライン（star 25,000）は `docs/build.py` の定数。
  変えたくなったら、変えずに人間に上げる。
- **分類軸を作り替えない。** 4 層（L0〜L3）と副軸（terminal / ide / cloud）の定義は変更対象外。
  L3 の割り直しは検討中の案件だが、**この定期更新の中で勝手に実施しない。**
- **項目を削除しない。** 終了したものは `ended` を埋めて残す。
- **モデル名と価格を書かない。** 変化が速すぎて更新周期に合わない。意図的な除外であって漏れではない。
- **`docs/index.html` を直接編集しない。** 生成物なので次のビルドで消える。
- **`docs/data/metrics.json` を手で編集しない。** 実測値の置き場所であって、意見の置き場所ではない。
- **コミットやプッシュを勝手にしない。** 変更をワークツリーに残して報告するところまで。

## 迷ったときの扱い

情報が矛盾する、あるいは終了したのか単に止まっているのか判断がつかない場合:

1. 既存の値を**消さない**
2. その項目に `status_note` フィールドを足し、何が不明なのかを一文で書く
3. 報告の「人間の判断が要る」欄に挙げる

勝手に決めない。このランドスケープは、分からないことを分からないと書いてあることに価値がある。

## 冪等性

`fetch_metrics.py` と `build.py` はどちらも、実質的な変更が無ければファイルに触らない。
したがって **何も変わっていない週に流しても `git status` は空のまま**になる。
もし変更が無いはずなのに差分が出たら、それはスクリプト側の不具合なので報告する。

なお `fetch_metrics.py` は star の微小な増減（±50 または 1% 未満のうち大きいほう）を
変化とみなさない。大きなリポジトリの star は数秒で動くので、この閾値が無いと毎回差分が出る。

## 失敗の扱い

| 起きたこと | どうするか |
|---|---|
| GitHub のレート制限 | `gh auth status` を確認する。未認証だと 60 req/h しかない。認証しても足りない場合は時間を置いて再実行し、**部分的な結果でファイルを上書きしない**（スクリプトが前回値を温存するので、失敗項目はそのまま残る） |
| ネットワーク断 | 既存データは壊れない。失敗一覧が出るので、そのまま報告して終了する |
| リポジトリが 404 | 消えたか非公開になったか改名された。調べて `repo` を直すか、`ended` を埋める。**推測で消さない** |
| 改名を検出 | `repo` を直し、移管の経緯を調べて `summary` に反映し、再実行する |
| `build.py` が警告を出す | 警告を消してから終わる。消せない場合は理由を添えて報告する |

## 報告の形式

最後に、この形で出力する。

```
## 更新結果（YYYY-MM-DD）

### 変わったもの
- <名前>: <何がどう変わったか>（出典: <URL>）

### 追加したもの
- <名前>: <層> / <なぜ候補に挙がったか>

### 終了・改名を検出したもの
- <名前>: <経緯> → <後継 or なし>

### 人間の判断が要るもの
- <項目>: <何が決められなかったか>

### 変更なしの場合
今回は実質的な変更なし。<N> 項目を確認、うち <M> 件の star が動いたが閾値未満。
```
