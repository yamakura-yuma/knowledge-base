# AI コーディングツール・ランドスケープ

表示用の一枚物は [`index.html`](./index.html)（生成物。ブラウザで直接開ける）。
このファイルは、そこに載せきれない「どう作ってあるか」を書いたもの。

## 分類軸

主軸は **リクエストが通る経路上の位置**（アーキテクチャ上の層）。副軸は L1 の中だけで効く **実行場所**。

```
L0  モデル提供元      Anthropic / OpenAI / Google / DeepSeek …   参考。ツールではない
      ↑
L2  モデルアクセス層  OpenRouter / LiteLLM / Headroom …          ルーティング・課金・圧縮・観測
      ↑
L1  エージェント本体  Claude Code / OpenCode / Cursor / Devin …  計画とツール実行のループ
      ↑              └ 副軸: ターミナル / IDE / クラウド
L3  共通基盤          MCP / AGENTS.md / Agent Skills / apm …     全層の下敷き
```

この軸を採った理由は単純で、出発点の問い「OpenCode と OpenRouter をまとめて」が
**層の違うものを並べる問い**だったから。層で切ると役割が一意に決まり、
「両者は競合ではなく組み合わせるもの」という関係がそのまま見える。

検討して採らなかった軸:

| 軸 | 採否 | 理由 |
|---|---|---|
| 経路上の位置 | 主軸 | 役割が一意。層違いの無理な比較を避けられる |
| 実行場所 | 副軸 | L1 でしか効かないので主軸にできない |
| ビジネスモデル（OSS / 商用） | 不採用 | 分類ではなく表の列にした |
| 用途 | 不採用 | コーディング支援に絞ったので軸にならない |

### L3 は暫定

L3 にはプロトコル（MCP）、指示形式（AGENTS.md / Agent Skills）、配布（apm）、
実行の束ね（orca）、索引の供給（CodeGraph / graphify）、スキル集（ponytail）が同居している。
**明らかにもう一段割れるが、まだ割り方を確定させていない。**

確定させずに進めるかわりに、`registry.yaml` の L3 項目には `subkind` に気づいた性格を書いてある。
HTML には出していない（見出しにすると分類が確定したように見えるため）。
割り方が決まったら、`build.py` にサブセクションの処理を足すだけで済み、本文の書き直しは要らない。

## 母集団の決め方

「有名なツール」を感覚で選ぶと恣意的になるので、外部の実データを出発点にした。

1. Headroom（L2 のプロキシ）の `headroom wrap` 対応リスト — 実在の統合プロジェクトが
   「対応する価値がある」と判断して名指しした 15 個のエージェント CLI
2. そこに欠けている著名どころを補完
3. 調査中に GitHub の実測で浮かび上がったもの（Oh My Pi、Kilo Code、ponytail、CodeGraph など）
4. 終了・改名・統合したものを積極的に収集（タイムラインは墓場がないと意味を持たない）

**人気を理由に落としたものは無い。** 詳細を書くか、表の 1 行だけにするかの違いしかない。

## ファイルの役割

| パス | 役割 |
|---|---|
| `registry.yaml` | **正本。** 全項目の構造化データ。ここを編集する |
| `tools/<slug>.md` | 詳細ティアの本文。**散文のみ**（frontmatter は持たない。構造化データは registry 側） |
| `data/metrics.json` | GitHub API の実測値。`fetch_metrics.py` の出力。手で編集しない |
| `fetch_metrics.py` | star・push 日時・リリース数・アーカイブ状態を取得 |
| `build.py` | 上記 3 つから `index.html` を生成 |
| `index.html` | **生成物。直接編集しない** |
| `UPDATE_PROMPT.md` | 定期更新の手順書 |

## 使い方

```bash
uv run docs/fetch_metrics.py   # 実測値を更新
uv run docs/build.py           # HTML を生成
```

どちらも冪等で、実質的な変更が無ければファイルに触らない。
`fetch_metrics.py` は star の微小な増減（±50 または 1% 未満）を変化とみなさない。
大きなリポジトリの star は数秒単位で動くため、そうしないと定期実行のたびに中身の無い差分が出る。

## ティアの決め方

- **自動で詳細** — 現役（直近 90 日に push）かつ star 25,000 以上
- **手動で詳細** — `registry.yaml` に `tier: detail` と `tier_reason` を書いたもの。
  主に公開リポジトリが無く star で測れない商用製品。**カード上に「手動」と理由を明示する**
- **履歴** — それ以外。表の 1 行だけ

判断を数字に寄せつつ、寄せきれない部分は隠さず画面に出す、という方針。

## 書くときの約束

- 裏が取れない値は **null のまま**にする。推測で埋めない
- 各項目に `verified`（確認日）と最低 1 つの `sources` を持たせる。`build.py` が警告を出す
- モデル名と価格は書かない。更新周期に対して変化が速すぎて、必ず嘘になる
